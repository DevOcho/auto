# auto 0.9.0

**Every existing cluster has to be recreated once for this release, which resets
its local databases. Back them up first (steps below).**

## What changed

- **Envoy Gateway replaces ingress-nginx**, which was retired in March 2026.
  Pods are exposed with Gateway API HTTPRoutes in `.auto/routes.yaml`; see
  [Expose it with a route](https://devocho.github.io/auto/guides/routes/). A pod repo keeps its
  Ingress for anyone still on 0.8 until a later release removes it.
- **Newer Kubernetes.** New clusters run k3s v1.35.9 (Envoy Gateway needs 1.33
  or newer; 0.8 made 1.31 clusters). On a cluster made by 0.8, `auto start`
  stops and explains how to recreate it.
- **Faster start.** A fresh `auto start` on a two-node cluster took 97 and
  119 s in testing, against four to seven minutes in 0.8, and resuming an
  existing cluster about 35 s. What changed:
  - Docker Hub images the cluster pulls by itself (k3s's own pods, Envoy
    Gateway) now come from auto's local registry, through a `docker.io`
    mirror for the nodes. That saved about 35 s on each fresh start (134 and
    154 s without it), and a start no longer stalls when Docker Hub is slow.
    The first cluster after upgrading still pulls them from Docker Hub once.
  - Database ports are mapped when the cluster is created.
  - auto no longer waits for the ingress controller before loading pods.
  - minio's setup no longer holds up the start.
- **Fixes.**
  - MySQL could crash-loop after a restart: mysql, minio, redis and matomo
    shared one host directory. Each now has its own, pinned to one node.
  - Database creation no longer races MySQL's first boot, and a database that
    could not be created is no longer reported as created.
  - A database pod that never starts is reported instead of ignored.
- **Helm is no longer needed for ingress.** It is still needed for pods
  deployed with Helm charts.
- **New `agents:` setting** in `local.yaml` for the number of agent nodes.
- **Ports stay on your machine.** The sites, the MySQL, Postgres and Redis
  ports, the image registry and the Kubernetes API now listen on 127.0.0.1.
  Before, Docker published them on every network interface, so anyone on the
  same network could reach the databases with their fixed passwords. A team
  that shares one dev setup on a network it trusts can set
  `bind-address: 0.0.0.0` in `local.yaml`.
- **Removed:**
  - The HTTP routes to the MySQL, Postgres and Redis ports. They never served
    anything; the databases are still on their host ports.
  - The `matomo` system pod. An old `local.yaml` that still turns it on gets a
    note and the pod is skipped; you can delete its entry and its `registry:`
    image.

## Behavior changes from ingress-nginx

| | 0.8 (ingress-nginx) | 0.9 (Envoy Gateway) |
| --- | --- | --- |
| Request body limit | 1 MiB unless annotated (413 above it) | None; your app's own limit applies |
| Silent request | Cut after 60 s unless annotated, and GETs retried twice | Waits up to an hour; never retried |
| Long request while a pod starts or restarts | Dropped about 4 minutes later | Unaffected |
| Idle websocket | Closed after 60 s | Open for up to an hour |
| HTTP to HTTPS redirect | `force-ssl-redirect` annotation (308) | A redirect route (308); see the [HTTPS-only template](https://devocho.github.io/auto/guides/routes/#https-only) |
| Certificate refresh | Restarted the ingress controller | Picked up live |

What each nginx annotation becomes, and how to convert an Ingress, is in
[Moving from ingress-nginx](https://devocho.github.io/auto/guides/from-ingress-nginx/).

## Upgrading

1. With the cluster still running, back up the databases:

   ```bash
   mkdir -p ~/auto-backup
   kubectl exec deploy/mysql -- sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --all-databases --single-transaction --routines --events' > ~/auto-backup/mysql.sql
   kubectl exec deploy/postgres -- sh -c 'pg_dumpall -U "${POSTGRES_USER:-postgres}"' > ~/auto-backup/postgres.sql
   ```

   These do not cover MinIO files or Redis data; re-seed those, or copy them
   out first if you need them.

2. Install 0.9.0 and recreate the cluster, and the image registry so it too
   listens only on your machine:

   ```bash
   auto update
   auto stop --delete-cluster
   k3d registry delete k3d-registry.local
   auto start
   ```

   The new registry starts empty, so this start downloads and builds every
   image once. Keep the old registry by skipping its line; `auto start` then
   reminds you it is still open to your network.

3. Re-seed each pod, or restore the backup:

   ```bash
   auto seed <pod>
   # or
   kubectl exec -i deploy/mysql -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD"' < ~/auto-backup/mysql.sql
   kubectl exec -i deploy/postgres -- sh -c 'psql -U "${POSTGRES_USER:-postgres}" -d postgres' < ~/auto-backup/postgres.sql
   ```

4. Pods whose repo has no `.auto/routes.yaml` yet start fine but do not answer;
   `auto start` lists them. Their repos need the
   [routes file](https://devocho.github.io/auto/guides/routes/).
   If you run new-d8, it also needs DevOcho/new-d8#645, which switches it to
   auto's mailpit.

Optional: `local.yaml` still lists `kubectl apply -f ~/.auto/k3s/{mysql,postgres,redis}/ingress.yaml`
under those system pods. auto skips those lines now; you can delete them.

## Going back to 0.8.3

```bash
auto update 0.8.3
auto stop --delete-cluster
auto start
```

0.8.3 cannot use a cluster made by 0.9 (there is no ingress-nginx in it), so
the cluster is recreated again and its databases reset; back them up first as
above.
