# auto 0.9.3

**Coming from 0.8? Read the
[0.9.0 release notes](https://devocho.github.io/auto/releases/0.9.0/) first:**
every existing cluster has to be recreated once, which resets its local
databases.

## What changed

- **Linux on ARM.** A new `linux-arm64` download runs on 64-bit ARM: ARM
  servers such as AWS Graviton, ARM laptops, Raspberry Pis with a 64-bit OS,
  and Windows on ARM through WSL2. The installer picks it by itself. Every
  system pod in the default `local.yaml` runs on ARM. SQL Server doesn't,
  because Microsoft publishes no ARM image of it.
- **Every release is started before it is published.** Each Linux build, on
  x86-64 and on ARM, now runs a real `auto start` with the default config on
  its own architecture: a first start, a resume and a recreate, with the site
  answering over HTTPS each time. The release waits for all of them.
- **ProxySQL 3.0.2**, up from 2.3.2, which has no ARM image. Tested with
  auto's own ProxySQL config in front of MySQL 8.0.
- **Older k3s and Envoy Gateway images are dropped from `registry:`.** auto
  adds every image the cluster runs to `local.yaml`, so each k3s upgrade left
  the old versions behind, and every new machine downloaded them all. Once
  the cluster runs a newer version of one of these images, auto now removes
  the older ones from the list. Images your own pods use are never removed.
- **Images are cached several at a time** at the end of a start, instead of
  one after another. On a new machine that step took about a minute.
- **A resumed cluster is ready before auto uses it.** Right after a resume,
  the Kubernetes API answers before it takes `kubectl apply`, so the first
  system pod's commands retried every 2 s, and one resume took 48 s instead
  of about 20. auto now waits for the API to be ready first.

## Upgrading

```bash
auto update
```

On an ARM machine, install with the installer, which picks the ARM download:

```bash
curl -fsSL https://www.devocho.com/auto.sh | bash
```
